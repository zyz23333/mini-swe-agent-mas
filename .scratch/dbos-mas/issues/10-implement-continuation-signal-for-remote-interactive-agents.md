# Implement Continuation Signal for Remote Interactive Agents

Status: ready-for-agent
Type: AFK

## Parent

.scratch/dbos-mas/PRD.md

## What to build

Implement `mini-mas continue <workflow-id> "message"` so a Parent Agent Workflow can ask a waiting Child Agent Workflow to keep working from its existing trajectory. The Continuation Signal should become a normal user message in the child trajectory, with metadata identifying it as a MAS continuation.

This slice should prove that a Remote Interactive Agent can produce a submission, wait for parent direction, continue with the same linear message history, and produce a later observable result.

## Acceptance criteria

- [ ] `mini-mas continue <workflow-id> "message"` sends a Continuation Signal to a waiting Child Agent Workflow.
- [ ] The Continuation Signal is injected into the child trajectory as a normal user message.
- [ ] Continuation metadata identifies the message as MAS continuation without changing model adapter action parsing.
- [ ] The child resumes from its existing message history rather than starting a new workflow.
- [ ] Continuation delivery and receipt use parent-to-child DBOS messages at the async Agent Workflow layer, outside DBOS steps.
- [ ] The resumed child can produce a second submission or terminal status visible through status/wait.
- [ ] Tests cover first submission, waiting state, continuation, trajectory message injection, second submission, and observation formatting.

## Agent Brief

**Category:** enhancement
**Summary:** Implement Continuation Signals so Remote Interactive Agents can resume from their existing trajectory after parent direction.

**Current behavior:**
The MAS subsystem can start Root Agent Workflows, start Child Agent Workflows through Detached Spawn and Waited Spawn, expose lightweight Child Status Events through `mini-mas status`, and synchronize on Child Agent Workflow First Observable Events through `mini-mas wait`.

Child Agent Workflows already become Remote Interactive Agents after their first submission: they publish `waiting_for_parent` status, set a First Observable Event, persist their Trajectory Artifact, and wait for parent direction through a DBOS async receive path in the Agent Workflow layer. However, the current parent-direction signal is only received as a value at the waiting point. A user-facing `mini-mas continue <workflow-id> "message"` command does not yet send a Continuation Signal, and the child does not yet inject continuation content into its existing message history before continuing work.

**Desired behavior:**
`mini-mas continue <workflow-id> "message"` should send a Continuation Signal from a Parent Agent Workflow to a waiting Child Agent Workflow. The signal must be delivered through DBOS parent-to-child workflow messages at the async Agent Workflow layer, outside DBOS steps.

When the child receives a Continuation Signal, it should append the continuation as a normal user message to the same linear trajectory it already built before waiting. The message should preserve ordinary model-adapter behavior: model adapters should still receive a normal user message and should not need new action parsing logic or a separate MAS tool schema. The message should also include metadata identifying it as a MAS continuation so the Trajectory Artifact can distinguish parent continuation from the original task prompt.

After injecting the continuation message, the child should continue from the same in-memory message history and produce later observable behavior. A second submission should make the child parent-actionable again and visible through existing status and wait surfaces. Non-submission terminal states after continuation should also remain visible through existing status surfaces.

Invalid continue requests should fail clearly. A Parent Agent Workflow should not be able to continue the root workflow, a workflow outside the current Agent Workflow Tree, or a missing child workflow. Argument errors should return the same kind of model-visible command observation used by other workflow-layer MAS commands.

**Key interfaces:**
- `mini-mas continue <workflow-id> "message"` — workflow-layer MAS Command that validates target workflow identity and sends a Continuation Signal.
- Continuation Signal message shape — should include a signal type, the continuation content, source parent workflow identity where useful, and enough metadata to identify the resulting trajectory message as MAS continuation.
- Parent-to-child DBOS messaging — must use async workflow-control APIs such as `send_async` from Agent Workflow code, not DBOS steps.
- Child parent-direction receive path — should distinguish Continuation Signals from other parent-direction signal types and resume the agent loop for continuation.
- Agent Workflow message history — should append the continuation as a normal `user` message with MAS continuation metadata, preserving the existing linear history model.
- Child Status Event and First Observable Event behavior — should make the resumed child observable after second submission or terminal state without replacing full history with DBOS event data.
- Trajectory Artifact persistence — should persist the injected continuation message and the later submission or terminal state at the deterministic child artifact path.

**Acceptance criteria:**
- [ ] `mini-mas continue <workflow-id> "message"` sends a Continuation Signal to a waiting Child Agent Workflow in the current Agent Workflow Tree.
- [ ] The command validates that the target is a descendant Child Agent Workflow, not the Root Agent Workflow or a workflow outside the current tree.
- [ ] Continuation delivery uses parent-to-child DBOS workflow messages at the async Agent Workflow layer, outside DBOS steps.
- [ ] The waiting child receives the Continuation Signal through the existing parent-direction receive path or an equivalent async workflow-control receive path.
- [ ] The child injects the continuation into its existing trajectory as a normal `user` message.
- [ ] The injected user message includes metadata identifying it as a MAS continuation without requiring model adapter action parser changes.
- [ ] The child resumes from the same linear message history rather than starting a new workflow or rebuilding from only the original task.
- [ ] The resumed child can produce a second submission.
- [ ] After a second submission, existing `status` and `wait` surfaces expose the later parent-actionable result with the deterministic Trajectory Artifact path.
- [ ] Non-submission terminal states after continuation remain visible through existing status surfaces.
- [ ] The Trajectory Artifact includes the first submission, waiting state history, injected continuation message, and later submission or terminal state.
- [ ] Model-specific observation formatting remains intact for text, toolcall, and Responses API style deterministic models.
- [ ] Tests cover first submission, waiting state, continuation command dispatch, DBOS message send/receive behavior, trajectory message injection, second submission, and observation formatting.

**Out of scope:**
- Implementing the neutral `mini-mas close` command or final Close Signal semantics.
- Treating a Continuation Signal as acceptance, rejection, cancellation, retry, or fork.
- Adding a separate model tool schema for MAS.
- Changing model adapter action parsers.
- Adding dedicated history, logs, grep, or inspector commands.
- Solving Shared Workspace isolation.
- Claiming exactly-once semantics for arbitrary model or bash side effects.
