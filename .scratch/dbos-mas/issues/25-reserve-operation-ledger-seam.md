# Reserve an Operation Ledger seam for DBOS step side-effect recovery

Status: ready-for-human
Category: enhancement
Type: HITL

## Parent

## Refactor map reference

This issue must follow `.scratch/dbos-mas/issues/16-record-mas-deep-module-refactor-map.md` and any design note produced from it. Preserve the module boundaries, DBOS step/workflow-control boundaries, and out-of-scope constraints recorded there; do not invent alternate MAS module names, authority models, DBOS behavior, or command fallbacks.

## What to build

Design, but do not implement, the future **Operation Ledger** **Seam** for model query and ordinary bash side-effect recovery. The design should describe where `query_model_step` and `execute_bash_step` would pass through an operation-recording **Interface** so DBOS recovery can later distinguish started, completed, reusable, retryable, and fail-closed operations.

This issue should keep ADR-0004's warning visible: DBOS step checkpointing and `retries_allowed=False` do not provide exactly-once semantics for arbitrary model calls or bash commands.

## Acceptance criteria

- [ ] A design note identifies the future **Operation Ledger** **Interface** for model query and bash execution operations.
- [ ] The note states which data would need stable operation identifiers without choosing a final storage schema.
- [ ] The note preserves the current DBOS rule that model calls and bash execution are external side effects inside steps.
- [ ] The note explains why this slice does not implement the ledger or claim exactly-once semantics.
- [ ] No production recovery policy or persistence schema is introduced without separate approval.

> **Category:** enhancement
> **Summary:** Reserve the future Operation Ledger seam for model-query and ordinary-bash side-effect recovery without implementing ledger storage or recovery policy.
>
> **Current behavior:**
> MAS currently treats model queries and ordinary bash execution as external side effects wrapped by DBOS steps. Model calls pass through `query_model_step`; ordinary bash actions pass through `execute_bash_step`; Standalone MAS Commands remain intercepted at the Agent Workflow layer and do not enter ordinary bash execution.
>
> ADR-0004 remains the controlling recovery warning: DBOS step checkpointing and `retries_allowed=False` do not provide exactly-once semantics for arbitrary model calls or bash commands. If a process crashes after the external side effect happens but before DBOS records the step result, recovery may repeat the side effect unless MAS later adds an additional guard.
>
> The prior blocker, `.scratch/dbos-mas/issues/21-restore-mini-shaped-agent-workflow-loop.md`, is now `done`, so the mini-shaped Agent Workflow loop and the `query_model_step` / `execute_bash_step` boundaries are available as the design baseline.
>
> **Desired behavior:**
> A human should write a design note that reserves the future Operation Ledger Interface and Seam for model query and ordinary bash execution operations. The note should describe where the operation-recording interface would sit relative to the existing DBOS step wrappers and which operation inputs need stable identifiers, while deliberately avoiding final storage schema, production recovery policy, retry semantics, or exactly-once claims.
>
> The design should keep the current DBOS boundary intact: model calls and ordinary bash execution remain external side effects inside DBOS steps, while MAS command interception and workflow-control operations remain Agent Workflow responsibilities.
>
> **Key interfaces:**
> - `query_model_step` - the DBOS step boundary for model-query side effects; the future Operation Ledger seam should account for model operation identity before any policy can decide whether to reuse, retry, or fail closed.
> - `execute_bash_step` - the DBOS step boundary for ordinary bash side effects; the future Operation Ledger seam should account for command operation identity without treating arbitrary bash as exactly-once safe.
> - Operation Ledger Interface - a future operation-recording contract that can distinguish at least started and completed operations, and can leave room for later reusable, retryable, and fail-closed decisions.
> - Stable operation identifiers - the design should name the input data that would need to contribute to stable logical operation IDs without choosing a final persistence schema.
