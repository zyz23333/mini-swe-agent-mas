# Convert MAS coordination to async Agent Workflows

Status: done
Type: AFK

## What to build

Refactor the MAS Agent Workflow layer from synchronous DBOS workflow-control calls to async DBOS workflows and awaited DBOS workflow-control APIs. This is a prerequisite for waited spawn, first-observable waiting, Continuation Signals, Close Signals, and recursive Descendant Agent Workflow coordination.

This slice should preserve the external behavior already implemented for `mini-mas run`, `mini-mas status`, and detached `mini-mas spawn`, while changing the internal workflow-control shape so later coordination slices do not need to mix feature work with architecture migration.

## Agent Brief

**Category:** enhancement
**Summary:** Convert MAS Agent Workflow coordination from synchronous DBOS workflow-control calls to async Agent Workflows and awaited DBOS workflow-control APIs.

**Current behavior:**
The MAS subsystem already supports the initial Root Agent Workflow path, lightweight status inspection, and Detached Spawn with deterministic Child Agent Workflow IDs. It keeps ordinary model calls, bash execution, and trajectory persistence behind DBOS step boundaries, and it keeps Standalone MAS Commands routed through the Agent Workflow layer instead of ordinary bash execution.

The current Agent Workflow coordination shape is still synchronous. Root and Child Agent Workflows are synchronous DBOS workflows, root startup uses synchronous workflow start and result handles, child startup uses synchronous queue enqueue behavior, and status/event lookup uses synchronous DBOS workflow-control APIs. This works for the already implemented `mini-mas run`, `mini-mas status`, and detached `mini-mas spawn` behavior, but it is the wrong internal shape for later Waited Spawn, First Observable Event waiting, Continuation Signals, Close Signals, and recursive Descendant Agent Workflow coordination.

**Desired behavior:**
The Agent Workflow layer should use async DBOS workflows and awaitable DBOS workflow-control APIs for MAS coordination. Root and Child Agent Workflows should be async workflows, and workflow-layer MAS command dispatch should be able to await coordination operations such as child workflow startup, status/event lookup, and future wait/send/receive operations.

The refactor must preserve the external behavior already implemented for `mini-mas run`, `mini-mas status`, Detached Spawn, MAS command routing, model query execution, bash execution, and trajectory persistence. Detached Spawn should still return immediately with child Workflow Tree IDs, Run Directory, and Trajectory Artifact paths; it must not wait for child submission or final workflow completion.

The DBOS boundary should remain clear. Model calls, ordinary bash execution, and trajectory persistence remain checkpointed through DBOS step boundaries. Workflow-control operations such as child workflow creation, queueing, status/event lookup, waiting, send, and receive should remain outside DBOS steps and should be awaited at the Agent Workflow layer when invoked from async workflow code.

Runtime startup and tests should use async DBOS APIs or async-compatible wrappers where DBOS requires them. Synchronous CLI entrypoints may remain user-facing synchronous commands if they bridge cleanly into the async DBOS runtime without changing the external CLI contract.

**Key interfaces:**
- Root Agent Workflow and Child Agent Workflow definitions - should become async DBOS workflows while preserving their existing input and result contracts.
- MAS command dispatch - should remain workflow-layer coordination logic and become awaitable where it performs workflow-control operations.
- Child Agent Workflow startup - should use async-compatible queue or workflow startup APIs while preserving deterministic Workflow Tree IDs and Detached Spawn result metadata.
- Status lookup and status event access - should use async-compatible DBOS status/event APIs from async Agent Workflow code while preserving non-blocking status behavior.
- Runtime startup helpers - should start Root Agent Workflows through async DBOS APIs or a safe synchronous wrapper around the async path, preserving the existing `mini-mas run` output contract.
- DBOS step functions for model query, ordinary bash execution, and trajectory persistence - should remain the side-effect checkpoint boundary and should not absorb workflow-control operations.

**Acceptance criteria:**
- [x] Root Agent Workflow and Child Agent Workflow are implemented as async DBOS workflows.
- [x] MAS command dispatch, child workflow startup, status lookup, and workflow-control helpers are awaitable at the Agent Workflow layer.
- [x] Detached Spawn still returns child Workflow Tree IDs, Run Directory, and Trajectory Artifact paths without waiting for child submission or final completion.
- [x] Existing model query, bash execution, and trajectory persistence behavior remain behind DBOS step boundaries.
- [x] Workflow-control operations such as child workflow creation, queueing, status/event lookup, waiting, send, and receive remain outside DBOS step functions.
- [x] Runtime startup uses async DBOS APIs or async-compatible wrappers where DBOS requires them, while preserving the existing external CLI behavior.
- [x] Tests cover the existing `mini-mas run`, `mini-mas status`, Detached Spawn, MAS command routing, and trajectory persistence behavior after the async refactor.
- [x] Tests or assertions cover that async workflow startup and async child startup use awaitable DBOS workflow-control APIs rather than the prior synchronous workflow-control shape.

**Out of scope:**
- Implementing Waited Spawn behavior.
- Implementing `mini-mas wait`.
- Implementing Continuation Signals or Close Signals.
- Implementing recursive Descendant Agent Workflow behavior beyond preserving an async-compatible foundation for it.
- Changing the user-facing command syntax or output contract for already implemented `mini-mas` commands.
- Moving model query, ordinary bash execution, or trajectory persistence out of DBOS step boundaries.
- Solving Shared Workspace isolation or exactly-once semantics for arbitrary bash side effects.
