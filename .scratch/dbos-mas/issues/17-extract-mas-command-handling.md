## What to build

Move workflow-layer **MAS Command** handling behind one deep **Module** so the **Agent Workflow** loop no longer owns the `status`, `spawn`, `wait`, `continue`, and `close` dispatch tree directly. The loop should classify bash-shaped actions, reject non-standalone `mini-mas` usage, send standalone commands to the new command handler, and execute ordinary bash through the existing checkpointed bash step.

The new **Module** should preserve the current model-visible behavior while hiding command routing, command-specific argument parsing, and result construction behind a small **Interface**.

## Agent Brief

**Category:** enhancement
**Summary:** Extract workflow-layer MAS Command dispatch behind one small command handler interface.

**Current behavior:**
The Agent Workflow action execution path already classifies bash-shaped actions before execution. Ordinary bash actions go through the checkpointed bash execution step, invalid `mini-mas` shell compositions return a model-visible correction, and Standalone MAS Commands are intercepted at the workflow layer. However, the workflow-layer action path still owns the subcommand dispatch tree for `status`, `spawn`, `wait`, `continue`, and `close`, along with command-specific argument parsing and model-facing command result construction.

**Desired behavior:**
The Agent Workflow loop should stay focused on the high-level execution route:

- classify each bash-shaped action once;
- reject non-standalone `mini-mas` shell compositions before ordinary bash execution;
- pass already-classified Standalone MAS Commands to one deep command handling module;
- execute ordinary bash through the existing checkpointed bash execution step;
- return model-specific observation messages through the existing model formatter.

The new command handling interface should hide command routing, command-specific argument parsing, and observation-result construction for Standalone MAS Commands while preserving the current model-visible behavior. It must follow the resolved direction from issue 16, which the maintainer confirmed is the authoritative refactor map. Do not invent alternate MAS module names, authority models, DBOS behavior, or command fallbacks.

**Key interfaces:**
- `MasCommandClassification` - the command handler should accept an already-classified Standalone MAS Command. It should not re-parse raw shell command safety or create a second interpretation of Standalone MAS Command validity.
- `classify_mas_command()` - remains the shell-level classifier for ordinary bash, invalid shell composition, and Standalone MAS Command routing.
- `execute_agent_workflow_actions()` - should keep returning model-specific observation messages for all action outcomes.
- `execute_bash_step()` - remains the only ordinary bash execution path for Agent Workflow actions.
- The new command handler interface - should return the existing bash observation result shape with `output`, `returncode`, `exception_info`, and `extra`, so existing model observation formatters keep working unchanged.

**Acceptance criteria:**
- [ ] Standalone MAS Commands are still intercepted at the Agent Workflow layer and are not sent to environment execution or DBOS step wrappers.
- [ ] The Agent Workflow loop no longer owns the direct `status`, `spawn`, `wait`, `continue`, and `close` dispatch tree.
- [ ] Command-specific argument parsing for `status`, `spawn`, `wait`, `continue`, and `close` is hidden behind the command handler interface.
- [ ] Command result construction for Standalone MAS Commands is hidden behind the command handler interface.
- [ ] Non-standalone `mini-mas` shell compositions still return the existing clear model-visible correction and do not execute as ordinary bash.
- [ ] Ordinary bash actions still execute through the checkpointed bash execution step.
- [ ] `execute_agent_workflow_actions()` still returns model-specific observation messages for Standalone MAS Commands, invalid `mini-mas` shell compositions, and ordinary bash actions.
- [ ] Existing tests for command classification, action execution dispatch, ordinary bash fallback, and model-specific observation formatting pass.
- [ ] Behavior-visible tests for existing `status`, `spawn`, `wait`, `continue`, and `close` command outputs still pass.

**Out of scope:**
- Renaming the main Agent Workflow module to `mas_agent`.
- Introducing `DBOSCoordinationAdapter`.
- Extracting the Direct Child Authority Policy into its own module.
- Moving child spawn, wait, status event, First Observable Event, Continuation Signal, or Close Signal coordination into separate modules.
- Changing the Direct Child Authority Policy.
- Adding Authority Grants, subtree-wide authority, tree-wide Root Agent Workflow authority, external operator authority, new command fallbacks, or new DBOS behavior.
- Changing model action parsing, model observation formatting, or the ordinary bash execution semantics.
