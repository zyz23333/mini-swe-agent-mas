Status: done
Type: AFK

## What to build

Implement the ordinary Agent Workflow path for model calls and bash execution through DBOS steps. A Root Agent Workflow should query a deterministic model, execute ordinary bash through a DBOS step, format observations through the existing model adapter behavior, persist the trajectory, and return terminal state when the task submits or limits are exceeded.

Workflow-control operations must remain outside DBOS steps. This slice should make the non-MAS-command path durable and testable before child coordination is added.

- [x] Ordinary bash execution runs through a DBOS step and successful command outputs can be replayed by DBOS recovery.

- [x] Tests use deterministic model and environment doubles, not real model providers.
- [x] Tests validate externally visible behavior: command result, observation message shape, terminal state, and saved Trajectory Artifact.

## Agent Brief

**Category:** enhancement
**Summary:** Implement the ordinary Agent Workflow loop with DBOS-checkpointed model calls, bash execution, and trajectory persistence.

**Current behavior:**
The MAS subsystem has an isolated `mini-mas run` entrypoint, a minimal Root Agent Workflow, deterministic Root Workflow Tree IDs, deterministic Run Directory and Trajectory Artifact paths, and workflow-layer classification for Standalone MAS Commands. The current Root Agent Workflow only persists a minimal started trajectory artifact. It does not yet run an ordinary Agent Workflow loop, does not query a model through a DBOS step, does not execute ordinary bash through a DBOS step, and does not persist the resulting message history as the Trajectory Artifact.

The existing non-MAS agent loop provides the behavioral reference: initialize system and user messages, query the model, execute bash-shaped actions, format outputs back through the model adapter's observation formatter, save the trajectory, and stop when an exit/submission state is reached or limits are exceeded.

**Desired behavior:**
A Root Agent Workflow should support the ordinary non-child-coordination path end to end. It should initialize an Agent Workflow trajectory from deterministic model and environment inputs, query the model through a DBOS step, route actions according to MAS command classification, execute ordinary bash through a DBOS step, format observations using the same model-specific adapter behavior as ordinary mini-swe-agent, persist the real Trajectory Artifact, and return a terminal state when the task submits or configured limits are exceeded.

Workflow-control operations must remain outside DBOS steps. Standalone MAS Commands should continue to be handled by workflow-layer MAS dispatch, and invalid shell compositions containing `mini-mas` should continue to return a clear correction observation without entering ordinary bash execution. This slice should not implement child workflow coordination; it should make the ordinary model-and-bash path durable and testable before spawn/wait/continue/close behavior is added.

`limits_exceeded` should be represented as a terminal MVP state. It should be visible in the workflow result and persisted Trajectory Artifact in the same broad shape as other terminal states.

**Key interfaces:**
- Agent Workflow inputs - should carry enough deterministic model, environment, task, limit, and artifact metadata to run this ordinary path in tests without real model providers.
- Model query step - should wrap ordinary model querying in a DBOS step so successful model responses are checkpointed and can be replayed by DBOS recovery.
- Bash execution step - should wrap ordinary environment command execution in a DBOS step so successful command outputs are checkpointed and can be replayed by DBOS recovery.
- MAS command routing - should classify each bash-shaped action before execution, route Standalone MAS Commands to workflow-layer dispatch, reject invalid MAS shell compositions, and send only ordinary bash actions into the bash execution step.
- Observation formatting - should use existing model adapter observation formatting so text, toolcall, and Responses API style models receive observations in their expected shape.
- Trajectory Artifact persistence - should save the real Agent Workflow messages, model stats, terminal state, submission, Run Directory, Workflow Tree ID, and exact Trajectory Artifact path to the deterministic artifact path for the workflow.
- Workflow result - should return terminal state and artifact metadata that external callers can inspect without reading DBOS internals.

**Acceptance criteria:**
- [x] A Root Agent Workflow can run an ordinary deterministic model action that executes ordinary bash and returns the command result through the model-specific observation path.
- [x] Model calls run through a DBOS step, and tests prove successful model responses can be replayed from DBOS step results during recovery-style execution.
- [x] Ordinary bash execution runs through a DBOS step, and tests prove successful command outputs can be replayed from DBOS step results during recovery-style execution.
- [x] Standalone MAS Commands are classified before bash execution and remain routed to workflow-layer dispatch rather than entering the ordinary bash step.
- [x] Invalid shell compositions containing `mini-mas` still produce a correction observation and do not execute as ordinary bash.
- [x] The Agent Workflow preserves the high-level data flow `model message -> actions -> outputs -> model-specific observation messages`.
- [x] `limits_exceeded` is returned as a terminal MVP state and persisted into the Trajectory Artifact.
- [x] The saved Trajectory Artifact contains the actual Agent Workflow message history, terminal state, model stats, Run Directory, Workflow Tree ID, and exact Trajectory Artifact path.
- [x] Tests use deterministic model and environment doubles, not real model providers or real external services.
- [x] Tests validate externally visible behavior: command result, observation message shape, terminal state, workflow result metadata, and saved Trajectory Artifact contents.

**Out of scope:**
- Implementing Child Agent Workflows.
- Implementing `mini-mas spawn`, `status`, `wait`, `continue`, or `close` behavior beyond the existing placeholder workflow-layer dispatch.
- Implementing Remote Interactive Agent lifecycle, Continuation Signals, Close Signals, Child Status Events, or child workflow queues.
- Solving Workspace Isolation, Operation Ledger behavior, or exactly-once semantics for arbitrary bash commands.
- Adding a separate MAS-specific model tool schema or changing existing model-side action parsers.
- Moving workflow-control operations such as child workflow creation, send, receive, wait, or queue operations into DBOS steps.
