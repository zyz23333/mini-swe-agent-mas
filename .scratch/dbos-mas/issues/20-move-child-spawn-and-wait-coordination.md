# Move Child Workflow spawn and wait behavior into a Child Coordination Module

Status: done
Category: enhancement
Type: AFK

## Refactor map reference

This issue must follow `.scratch/dbos-mas/issues/16-record-mas-deep-module-refactor-map.md` and any design note produced from it. Preserve the module boundaries, DBOS step/workflow-control boundaries, and out-of-scope constraints recorded there; do not invent alternate MAS module names, authority models, DBOS behavior, or command fallbacks.

## What to build

Move **Detached Spawn**, **Waited Spawn**, and `mini-mas wait` behavior into a Child Coordination **Module**. The **Module** should own deterministic child Workflow Tree ID allocation, child workflow enqueueing, child metadata, wait-any and wait-all synchronization, timeout summaries, and still-running child workflow IDs.

The workflow-layer command handler should call this **Module** instead of assembling child spawning and waiting behavior inline.

## Acceptance criteria

- [x] `mini-mas spawn` still starts one **Child Agent Workflow** per task and returns child workflow IDs, run directory, and trajectory artifact paths.
- [x] Child Workflow Tree IDs remain deterministic and use the existing `-cNNN` suffix behavior.
- [x] `mini-mas spawn` remains detached by default.
- [x] `mini-mas spawn --wait` defaults to wait-any behavior.
- [x] `mini-mas spawn --wait --all` waits until all started children first become observable.
- [x] `mini-mas spawn --wait --timeout` returns ready children and still-running child workflow IDs without cancelling, closing, failing, or retrying children.
- [x] `mini-mas wait` behavior remains compatible for wait-any, wait-all, one direct child, and timeout paths.

> **Category:** enhancement
> **Summary:** Move child spawn and wait coordination behind a dedicated Child Coordination Module.
>
> **Current behavior:**
> Detached Spawn, Waited Spawn, and `mini-mas wait` behavior are behaviorally covered, but their business coordination is still assembled across the workflow-layer command handler and workflow orchestration helpers. The system already has a Direct Child Authority Policy module and a DBOS Coordination Adapter boundary, so this slice should deepen the module boundary around child spawning and child waiting without changing MAS semantics.
>
> Child workflow enqueueing, deterministic child Workflow Tree ID allocation, child metadata construction, First Observable Event waiting, transient `waiting_for_child` status publication, timeout summaries, and still-running child workflow ID calculation are currently spread across coordination-adjacent call sites. This makes future MAS refactors more likely to duplicate spawn/wait logic or blur the distinction between command presentation, DBOS primitive access, and child coordination behavior.
>
> **Desired behavior:**
> Introduce or deepen a Child Coordination Module that owns the workflow-layer domain behavior for:
>
> - Detached Spawn.
> - Waited Spawn.
> - `mini-mas wait` synchronization over direct children.
> - Deterministic child Workflow Tree ID allocation using the existing `-cNNN` suffix behavior.
> - Child Agent Workflow enqueueing through the existing DBOS Coordination Adapter.
> - Child metadata returned to command presentation.
> - Wait-any, wait-all, one-direct-child, and timeout coordination over First Observable Events.
> - Ready child snapshots, timeout flags, and still-running child workflow IDs.
>
> The workflow-layer command handler should call this module for child spawn/wait domain results instead of assembling those results inline. Command parsing and model-facing observation formatting should remain command-dispatch responsibilities. DBOS workflow-control primitives should continue to flow through the existing DBOS Coordination Adapter. Direct-child validation for explicit wait targets should continue to use the existing Direct Child Authority Policy.
>
> The refactor must preserve current model-visible behavior. `mini-mas spawn` remains detached by default. `mini-mas spawn --wait` waits for any child by default. `mini-mas spawn --wait --all` waits until all started children first become observable. `mini-mas spawn --wait --timeout` and `mini-mas wait --timeout` must return ready children plus still-running child workflow IDs without cancelling, closing, failing, retrying, or otherwise mutating children.
>
> `waiting_for_child` remains only the waiting parent workflow's latest lightweight status while a wait is active. It must not be published as a First Observable Event and must not authorize `continue` or `close`.
>
> **Key interfaces:**
> - Child Coordination Module - owns child spawn and wait domain behavior and returns structured MAS domain results rather than model-facing observation dictionaries.
> - DBOS Coordination Adapter - remains the MAS-specific wrapper around DBOS workflow-control primitives such as child enqueueing, status publication, First Observable Event waiting, direct child metadata/status lookup, and parent-direction message APIs.
> - Direct Child Authority Policy - remains the only authority path for explicit direct-child wait targets; this slice must not add new authority inputs or broaden scope.
> - Workflow-layer command handler - parses Standalone MAS Command arguments and converts structured Child Coordination results into the existing observation dictionary shape.
> - Workflow Tree ID helpers - preserve deterministic child ID allocation with sibling indexes and `-cNNN` suffixes.
>
