# Isolate Remote Interactive Agent continuation lifecycle

Preserve the module boundaries, DBOS step/workflow-control boundaries, and out-of-scope constraints recorded there; do not invent alternate MAS module names, authority models, DBOS behavior, or command fallbacks.

## What to build

Move **Remote Interactive Agent** lifecycle behavior into a dedicated **Module** or clearly isolated **Interface**. A **Child Agent Workflow** that reaches first submission should publish `waiting_for_parent`, publish its **First Observable Event**, save its trajectory, wait for a parent-direction message, and then either inject a **Continuation Signal** as a normal user message or close neutrally on a **Close Signal**.

The main **Agent Workflow** loop should not inline this entire continuation lifecycle.

## Acceptance criteria

- [x] A **Child Agent Workflow** enters `waiting_for_parent` after producing a submission.
- [x] The first parent-actionable state publishes a **First Observable Event** exactly as before.
- [x] A **Continuation Signal** becomes a normal user message in the existing trajectory.
- [x] After continuation, the child resumes from the same message history and can produce a second submission.
- [x] A **Close Signal** ends the **Remote Interactive Agent** neutrally without implying acceptance or rejection.
- [x] Failed and limits-exceeded child terminal states still publish parent-observable events as currently specified.
- [x] Existing continuation and close lifecycle tests pass.

> **Current behavior:**
> The MAS Agent Workflow behavior is already implemented and covered by tests: a Child Agent Workflow can publish `waiting_for_parent` after a submission, publish a First Observable Event, save its trajectory, wait for parent direction, inject a Continuation Signal as a normal user message, resume from the same message history, and close neutrally on a Close Signal.

Parent-direction signal payload construction, signal recognition, continuation user-message metadata, parent-direction receive behavior, submission waiting, and neutral close handling are not yet isolated as their own deep module or interface. This keeps the main Agent Workflow loop responsible for too much lifecycle detail.
>
> **Desired behavior:**
> Remote Interactive Agent lifecycle behavior should move behind a dedicated module or clearly isolated interface, preserving the existing behavior and model-visible outputs. The main Agent Workflow loop should read as high-level orchestration: run until a terminal message, delegate child submission continuation lifecycle handling when needed, continue on Continuation Signal, close neutrally on Close Signal, and otherwise publish/save terminal state as before.
>
> The isolated lifecycle boundary should own the parent-direction message concepts for Remote Interactive Agents: Continuation Signal payload shape, Close Signal payload shape, signal recognition, continuation user-message metadata, waiting for parent direction, and the state transitions around `waiting_for_parent` and neutral close. It must continue to use the DBOS Coordination Adapter for parent-direction messages and status/event publication rather than reaching around established boundaries.
>
> **Key interfaces:**
> - Remote Interactive Agent lifecycle interface - should expose a small workflow-layer contract for handling a submitted child that may wait for parent direction, resume from continuation, or close neutrally.

> - Continuation user-message conversion - should preserve the current behavior where a Continuation Signal becomes a normal user message with MAS metadata in the existing trajectory.
> - Child Status Event and First Observable Event publication - should preserve the existing event semantics and continue to publish the first parent-actionable state exactly as before.
> - DBOS Coordination Adapter - remains the boundary for DBOS workflow-control primitives; parent-direction receive/send and event publication stay in async Agent Workflow code, not DBOS steps.
