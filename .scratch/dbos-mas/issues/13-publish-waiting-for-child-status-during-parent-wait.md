# Publish waiting_for_child status during parent wait

Status: done
Category: enhancement
Type: AFK

## Parent

.scratch/dbos-mas/PRD.md

## What to build

Publish a lightweight `waiting_for_child` lifecycle state while an Agent Workflow is waiting for direct Child Agent Workflow First Observable Events.

This should cover both `mini-mas wait ...` and the wait phase of `mini-mas spawn --wait ...`. The status should be written after command arguments and direct-child scope have been validated, immediately before entering the First Observable Event wait. The workflow should publish `running` again after the wait exits, including timeout and exception paths.

This issue deliberately does not add wait context fields such as `wait_mode` or `waiting_child_workflow_ids`.

## Design constraints

- `waiting_for_child` means the current Agent Workflow is waiting for its own direct Child Agent Workflows.
- `waiting_for_child` is a latest lightweight status value only.
- `waiting_for_child` must not be written to `FIRST_OBSERVABLE_EVENT_KEY`.
- `waiting_for_child` must not be treated as parent-actionable.
- `mini-mas continue` and `mini-mas close` must continue to authorize only direct children whose latest status is `waiting_for_parent`.
- `mini-mas wait` should publish `waiting_for_child` only after it has found at least one valid direct child to wait on.
- `mini-mas spawn --wait` should publish `waiting_for_child` only after child workflows have been enqueued and before the waited-spawn wait phase starts.
- Invalid command arguments, missing Agent Workflow context, no current child workflows, and non-direct-child targets should not publish a transient `waiting_for_child` status.
- The implementation should use async DBOS event APIs from the Agent Workflow layer, not DBOS steps.
- The implementation should keep Root Agent Workflow behavior out of the acceptance criteria for this slice; future work may unify all Agent Workflow status behavior.

## Acceptance criteria

- [x] The status lifecycle state model accepts `waiting_for_child`.
- [x] `mini-mas wait --any`, `mini-mas wait --all`, bounded wait, and `mini-mas wait <workflow-id>` publish `waiting_for_child` before waiting when they have valid direct children to wait on.
- [x] `mini-mas wait` restores the waiting workflow's latest status to `running` after the wait completes or times out.
- [x] `mini-mas spawn --wait`, including wait-any, wait-all, and timeout variants, publishes `waiting_for_child` for the waiting phase.
- [x] `mini-mas spawn --wait` restores the waiting workflow's latest status to `running` after the wait completes or times out.
- [x] Invalid wait and waited-spawn commands do not publish `waiting_for_child`.
- [x] `waiting_for_child` is not published to the First Observable Event key.
- [x] A workflow whose latest status is `waiting_for_child` cannot be continued or closed unless it is also a valid direct child in `waiting_for_parent`, which should not happen in the current single-state model.
- [x] Existing direct-child authority behavior remains unchanged.
- [x] Tests cover normal wait completion, timeout restoration, waited-spawn restoration, invalid-command no-publish behavior, and the First Observable Event exclusion.

## Agent Brief

**Category:** enhancement

**Summary:** Add `waiting_for_child` as the lightweight status state published while an Agent Workflow waits for direct child First Observable Events.

**Current behavior:**

The MAS workflow layer publishes lightweight status snapshots through the `mini_mas_status` DBOS event key. Child workflows currently publish states such as `running`, `waiting_for_parent`, `closed`, `failed`, and `limits_exceeded`. Parent workflows that execute `mini-mas wait ...` or `mini-mas spawn --wait ...` wait on direct child First Observable Events, but their own latest status continues to look like `running` during the wait phase.

Direct-child authority is already enforced through `DBOS.workflow_id` and DBOS workflow metadata where `parent_workflow_id == DBOS.workflow_id`. First Observable Events are keyed by child workflow identifiers and are currently reserved for parent-actionable child states.

**Desired behavior:**

When an Agent Workflow enters a wait phase for direct children, publish a lightweight status snapshot with `lifecycle_state: waiting_for_child`. When the wait phase exits, publish `lifecycle_state: running` again. This makes recursive coordination observable: a parent can see that a direct child is not idle or stuck, but is itself waiting for its own children.

This should happen for both `mini-mas wait ...` and `mini-mas spawn --wait ...`. Do not add `wait_mode`, `waiting_child_workflow_ids`, or other wait-context fields in this slice.

`waiting_for_child` is not parent-actionable. It must not be written to `FIRST_OBSERVABLE_EVENT_KEY`, and it must not allow `mini-mas continue` or `mini-mas close`. Those commands must still require the target child status to be exactly `waiting_for_parent`.

**Implementation notes:**

- Add `waiting_for_child` to the status lifecycle state model.
- Prefer a small helper or `try`/`finally` wrapper so the status is restored to `running` on normal completion, timeout, and raised exceptions.
- Publish `waiting_for_child` only after the command is valid and there are direct children to wait on.
- In `mini-mas wait`, invalid arguments, no direct children, and non-direct-child targets should return their current errors without publishing `waiting_for_child`.
- In `mini-mas spawn --wait`, publish `waiting_for_child` only after children are started/enqueued and before `_wait_for_first_observable_events`.
- Do not publish `waiting_for_child` through `_publish_first_observable_event` or `_publish_first_observable_event_once`.
- Keep the existing `waiting_for_parent` checks in continuation and close signaling intact.

**Verification:**

- Run focused MAS tests, for example `uv run --python 3.11 pytest tests/run/test_mini_mas.py -q`.
- Run the broader relevant test suite if the implementation touches shared status formatting or command dispatch.
