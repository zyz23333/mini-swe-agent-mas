# Make Child Agent Workflows wait after first submission

Status: ready-for-agent
Type: AFK

## Parent

.scratch/dbos-mas/PRD.md

## What to build

Make a Child Agent Workflow enter `waiting_for_parent` after producing its first submission. The child should not terminate immediately after a submission; instead, it should publish lightweight status, set a First Observable Event, and wait for either a Continuation Signal or a Close Signal from its Parent Agent Workflow.

This slice should prove the Remote Interactive Agent lifecycle up to first submission and waiting state.

## Acceptance criteria

- [ ] A Child Agent Workflow records its first submission as `latest_submission`.
- [ ] After first submission, the child enters `waiting_for_parent` rather than terminating.
- [ ] The child sets a First Observable Event when it first reaches `waiting_for_parent`, `failed`, or `limits_exceeded`.
- [ ] The First Observable Event payload includes workflow ID, lifecycle state, latest submission or error, Run Directory, and exact Trajectory Artifact path.
- [ ] The Parent Agent Workflow can observe the child's waiting state through `mini-mas status`.
- [ ] Child-to-parent observable state is published through DBOS events keyed by the child workflow identifier, not through child-to-parent `send`.
- [ ] Waiting for parent direction is implemented in the async Agent Workflow layer with DBOS async receive APIs, not inside a DBOS step or a blocking final-result wait.
- [ ] The child's Trajectory Artifact includes the submitted output and remains available at the deterministic artifact path.
- [ ] Error and `limits_exceeded` paths publish appropriate terminal or latest error status.
- [ ] Tests cover first submission, transition to `waiting_for_parent`, status visibility, and trajectory persistence.

## Agent Brief

**Category:** enhancement
**Summary:** Make Child Agent Workflows become Remote Interactive Agents that wait for parent direction after their first submission.

**Current behavior:**
The MAS subsystem can start Root Agent Workflows, start Child Agent Workflows through Detached Spawn, expose lightweight Child Status Events through `mini-mas status`, and run MAS coordination through async Agent Workflows. Child workflows currently share the same terminal submission behavior as root workflows: after a submission is produced, the workflow reaches a terminal result instead of becoming parent-actionable and waiting for further direction.

Status snapshots already support lifecycle states such as `running`, `waiting_for_parent`, `closed`, `failed`, and `limits_exceeded`, plus `latest_submission` and `latest_error` fields. However, the Child Agent Workflow lifecycle does not yet publish a first-submission waiting state or wait for a Parent Agent Workflow after submission.

**Desired behavior:**
A Child Agent Workflow should record its first submitted output as `latest_submission`, persist the submitted trajectory data at its deterministic Trajectory Artifact path, publish lightweight observable status, set a First Observable Event, and enter `waiting_for_parent` instead of terminating immediately.

The First Observable Event should be set once per Child Agent Workflow when the child first reaches a parent-actionable state: `waiting_for_parent`, `failed`, or `limits_exceeded`. Its payload should include the child workflow ID, lifecycle state, latest submission or latest error when present, Run Directory, and exact Trajectory Artifact path.

Parent-observable child state should be published through DBOS events keyed by the child workflow identifier. It should not use child-to-parent workflow messages for status publication. After entering `waiting_for_parent`, the child should wait at the async Agent Workflow layer for either a Continuation Signal or a Close Signal from its Parent Agent Workflow. That wait must use DBOS async receive APIs or an equivalent async workflow-control API, not a DBOS step and not a blocking final-result wait.

Failure and `limits_exceeded` paths should remain parent-observable. They should publish appropriate terminal or latest error status and set the First Observable Event when they are the first parent-actionable state reached by the child.

**Key interfaces:**
- Child Agent Workflow lifecycle - should distinguish child post-submission behavior from root terminal submission behavior.
- Remote Interactive Agent state - should represent a submitted child waiting for parent direction as `waiting_for_parent`.
- Child Status Event or status snapshot shape - should expose workflow ID, lifecycle state, latest submission or error, Run Directory, and exact Trajectory Artifact path.
- First Observable Event - should be a one-time child-keyed DBOS event used by parent synchronization features, separate from final workflow results.
- Parent-to-child signal receive path - should wait for Continuation Signals or Close Signals in async Agent Workflow code, outside DBOS steps.
- Trajectory Artifact persistence - should preserve the submitted output and keep the artifact available at the deterministic child path while the child waits.

**Acceptance criteria:**
- [ ] A Child Agent Workflow records its first submission as `latest_submission`.
- [ ] After first submission, the Child Agent Workflow enters `waiting_for_parent` rather than terminating.
- [ ] The Child Agent Workflow publishes lightweight status with lifecycle state `waiting_for_parent`, Run Directory, exact Trajectory Artifact path, and latest submission.
- [ ] The Child Agent Workflow sets a First Observable Event the first time it reaches `waiting_for_parent`.
- [ ] The First Observable Event is also set if the child reaches `failed` or `limits_exceeded` before any submission wait state.
- [ ] The First Observable Event payload includes workflow ID, lifecycle state, latest submission or latest error when present, Run Directory, and exact Trajectory Artifact path.
- [ ] Parent-observable child state is published through child-keyed DBOS events, not child-to-parent workflow messages.
- [ ] `mini-mas status` can observe the child's `waiting_for_parent` state and latest submission without blocking on workflow completion.
- [ ] Waiting for parent direction is implemented in the async Agent Workflow layer with DBOS async receive APIs or equivalent async workflow-control APIs.
- [ ] Waiting for parent direction is not implemented inside a DBOS step and does not block on the child's final workflow result.
- [ ] The child's Trajectory Artifact includes the submitted output and remains available at the deterministic artifact path while the child waits.
- [ ] Failure and `limits_exceeded` paths publish appropriate latest error or terminal status and remain visible through status.
- [ ] Tests cover first submission, transition to `waiting_for_parent`, First Observable Event publication, status visibility, trajectory persistence, failure visibility, and `limits_exceeded` visibility.

**Out of scope:**
- Implementing the full user-facing `mini-mas continue` command.
- Implementing the full user-facing `mini-mas close` command.
- Defining final continuation message semantics beyond receiving a parent direction signal and preserving a clear waiting point for follow-up issues.
- Implementing Waited Spawn or the user-facing `mini-mas wait` command.
- Implementing recursive Descendant Agent Workflow coordination beyond preserving the child lifecycle behavior needed by descendants later.
- Solving Shared Workspace isolation.
- Claiming exactly-once semantics for arbitrary model or bash side effects.
