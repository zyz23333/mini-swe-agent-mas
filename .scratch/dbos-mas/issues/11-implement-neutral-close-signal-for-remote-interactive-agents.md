# Implement neutral Close Signal for Remote Interactive Agents

Status: ready-for-agent
Category: enhancement
Type: AFK

## Parent

.scratch/dbos-mas/PRD.md

## What to build

Implement `mini-mas close <workflow-id>` so a Parent Agent Workflow can tell a waiting Child Agent Workflow that no further work is requested. The Close Signal must be neutral: it ends the Remote Interactive Agent without implying acceptance, rejection, cancellation, or abort.

This slice should make the waiting lifecycle complete without adding kill, cancel, retry, fork, or queue mutation commands.

## Acceptance criteria

- [ ] `mini-mas close <workflow-id>` sends a Close Signal to a waiting Child Agent Workflow.
- [ ] A child receiving a Close Signal exits with lifecycle state `closed`.
- [ ] Status and wait output describe the child as `closed` without accepted/rejected/aborted semantics.
- [ ] Close delivery and receipt use parent-to-child DBOS messages at the async Agent Workflow layer, outside DBOS steps.
- [ ] Closing an already terminal or unknown workflow returns a clear error or no-op response consistent with the CLI behavior chosen in this slice.
- [ ] The child's final Trajectory Artifact remains available at the deterministic artifact path.
- [ ] Tests cover close from waiting state, closed status visibility, neutral wording, and repeated or invalid close behavior.

## Agent Brief

**Category:** enhancement
**Summary:** Add a neutral Close Signal so a Parent Agent Workflow can end a waiting Remote Interactive Agent without acceptance, rejection, cancellation, or abort semantics.

**Current behavior:**
Child Agent Workflows can become Remote Interactive Agents: after a submission they publish `waiting_for_parent`, expose `latest_submission`, persist their Trajectory Artifact, set a First Observable Event, and wait for parent direction through an async parent-to-child DBOS message receive path.

The MAS subsystem already supports Continuation Signals. A parent can send `mini-mas continue <workflow-id> "message"` to a waiting Child Agent Workflow, the signal is delivered through DBOS async messaging on the parent-direction topic, and the child injects the continuation as a normal user message before resuming the existing trajectory.

There is not yet a user-facing `mini-mas close <workflow-id>` command or a complete neutral close lifecycle. When a waiting child receives a non-continuation parent direction signal today, it does not publish a final `closed` lifecycle state as the intentional result of a Close Signal.

**Desired behavior:**
A Parent Agent Workflow should be able to run `mini-mas close <workflow-id>` to send a neutral Close Signal to a waiting Child Agent Workflow. The Close Signal means only that no further work is requested. It must not imply that the child output was accepted, rejected, cancelled, killed, aborted, retried, forked, or otherwise judged.

The close command should validate the target consistently with the existing parent-to-child signaling behavior: the target must be a Child Agent Workflow in the current Agent Workflow Tree, must be a descendant controlled by the current Parent Agent Workflow, must not be the Root Agent Workflow, and must currently be in `waiting_for_parent`.

If the target is unknown, outside the current Agent Workflow Tree, not a descendant controlled by the current Parent Agent Workflow, the Root Agent Workflow, already terminal, or otherwise not waiting for parent direction, the command should return a clear error and must not send a DBOS message. Repeated close after the child has reached `closed` should be treated as an already-terminal or not-waiting case rather than as acceptance, cancellation, or abort.

When a waiting Child Agent Workflow receives a Close Signal, it should publish final lightweight status with lifecycle state `closed`, keep the latest submission visible when present, persist the final Trajectory Artifact at the deterministic child path, and exit with terminal lifecycle state `closed`. Status and wait output should describe the child as `closed` with neutral wording only.

Close delivery and receipt must use parent-to-child DBOS messages at the async Agent Workflow layer. Workflow-control operations for close must remain outside DBOS steps.

**Key interfaces:**
- `mini-mas close <workflow-id>` MAS Command - should be accepted as a standalone MAS Command and dispatched at the Agent Workflow layer.
- External MAS CLI close command - should allow a user outside an Agent Workflow to send a Close Signal to a waiting Child Agent Workflow by workflow ID.
- Parent-to-child signal payload - should distinguish Close Signals from Continuation Signals without requiring a continuation message body.
- Remote Interactive Agent waiting loop - should recognize Close Signals and exit intentionally as `closed`.
- Child Status Event shape - should continue to expose workflow ID, lifecycle state, latest submission or error when present, Run Directory, and exact Trajectory Artifact path.
- Trajectory Artifact persistence - should preserve the child's final trajectory at the deterministic artifact path after close.

**Acceptance criteria:**
- [ ] `mini-mas close <workflow-id>` sends a neutral Close Signal to a waiting Child Agent Workflow.
- [ ] The external `mini-mas close <workflow-id>` CLI path sends the same kind of Close Signal as the in-workflow MAS Command path.
- [ ] Close delivery uses parent-to-child DBOS async messaging on the parent-direction channel, outside DBOS steps.
- [ ] A waiting Child Agent Workflow receives the Close Signal through the async Agent Workflow receive path, outside DBOS steps.
- [ ] A child receiving a Close Signal exits with lifecycle state `closed`.
- [ ] The child publishes final lightweight status with lifecycle state `closed`.
- [ ] The child's final status preserves `latest_submission` when the child had submitted before waiting.
- [ ] `mini-mas status` output describes the child as `closed` without accepted, rejected, cancelled, killed, or aborted wording.
- [ ] `mini-mas wait` and waited-spawn ready snapshot formatting can display `closed` neutrally when a close-related status snapshot is observed.
- [ ] Closing the Root Agent Workflow returns a clear error and does not send a DBOS message.
- [ ] Closing an unknown workflow or a workflow outside the current Agent Workflow Tree returns a clear error and does not send a DBOS message.
- [ ] Closing a sibling or otherwise non-descendant Child Agent Workflow from a Child Agent Workflow returns a clear error and does not send a DBOS message.
- [ ] Closing a workflow that is not in `waiting_for_parent`, including an already `closed`, `failed`, or `limits_exceeded` workflow, returns a clear already-terminal or not-waiting error and does not send a DBOS message.
- [ ] Repeated close after a child reaches `closed` does not imply acceptance, rejection, cancellation, or abort.
- [ ] The child's final Trajectory Artifact remains available at the deterministic artifact path.
- [ ] Tests cover close from waiting state, closed status visibility, neutral wording, Close Signal delivery/receipt through async DBOS messages, deterministic trajectory persistence, and invalid or repeated close behavior.

**Out of scope:**
- Adding kill, cancel, retry, fork, or queue mutation commands.
- Treating close as acceptance or rejection of a child's submission.
- Adding parent-level patch reconciliation, merge workflow, or output approval semantics.
- Changing Continuation Signal semantics beyond any small refactoring needed to share validation or signal dispatch code.
- Changing First Observable Event semantics or making close wait for final DBOS workflow results.
- Solving Shared Workspace isolation.
- Claiming exactly-once semantics for arbitrary model or bash side effects.
