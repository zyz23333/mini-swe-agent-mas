# Expose Child Status Events through `mini-mas status`

Status: ready-for-agent
Type: AFK

## Parent

.scratch/dbos-mas/PRD.md

## What to build

Expose lightweight Child Status Events for the current Agent Workflow Tree and make them visible through `mini-mas status`. Parent Agent Workflows and external users should be able to inspect the current tree without reading full trajectories or blocking on child completion.

The status surface should include coarse lifecycle state and fast decision data such as latest submission or latest error, while keeping full history in Trajectory Artifacts.

## Acceptance criteria

- [ ] Child Status Events include coarse states such as `running`, `waiting_for_parent`, `closed`, `failed`, and `limits_exceeded`.
- [ ] `mini-mas status` reports the current Agent Workflow Tree without blocking.
- [ ] `mini-mas status <workflow-id>` reports a specific descendant when it exists.
- [ ] Status output includes workflow ID, lifecycle state, latest submission or latest error when present, Run Directory, and exact Trajectory Artifact path.
- [ ] Full history remains in Trajectory Artifacts, not DBOS events.
- [ ] Tests cover tree status, specific workflow status, latest submission/error fields, and missing workflow behavior.

## Agent Brief

**Category:** enhancement
**Summary:** Expose lightweight Child Status Events through `mini-mas status` so parent workflows and external users can inspect the current Agent Workflow Tree without reading full trajectories.

**Current behavior:**
The MAS subsystem can start Root Agent Workflows, persist deterministic Run Directory and Trajectory Artifact paths, intercept Standalone MAS Commands at the workflow layer, checkpoint model/bash/artifact operations through DBOS steps, and perform Detached Spawn with deterministic Child Agent Workflow IDs.

Detached Spawn currently returns child metadata to the parent, but there is no durable lightweight status surface for the Agent Workflow Tree. `mini-mas status` is accepted by the workflow-layer MAS command dispatcher as a placeholder, and the External MAS CLI does not yet provide a real `status` command. Parent workflows and users must rely on returned spawn metadata or inspect Trajectory Artifacts directly.

**Desired behavior:**
MAS should publish lightweight Child Status Events for Agent Workflows and expose them through `mini-mas status`.

A status query should be non-blocking. It should report the current Agent Workflow Tree as known to the MAS subsystem, including each relevant Agent Workflow's Workflow Tree ID, coarse lifecycle state, latest submission or latest error when present, Run Directory, and exact Trajectory Artifact path.

`mini-mas status` should report the current Agent Workflow Tree. `mini-mas status <workflow-id>` should report a specific descendant when it exists and should return a clear not-found result when the workflow ID is not part of the current tree or cannot be found.

The status surface should stay lightweight. Full message history, full command output history, and detailed trajectory data must remain in Trajectory Artifacts, not in DBOS events or status records.

The implementation should support coarse lifecycle states including `running`, `waiting_for_parent`, `closed`, `failed`, and `limits_exceeded`. This issue should make those states representable and visible through status. The full Remote Interactive Agent behavior that transitions a submitted child into `waiting_for_parent` is handled by the follow-up issue for child workflows waiting after first submission.

**Key interfaces:**
- Child Status Event or equivalent status snapshot shape - should include workflow ID, lifecycle state, latest submission, latest error, Run Directory, and Trajectory Artifact path.
- Agent Workflow lifecycle publishing - should publish status at meaningful lifecycle transitions such as start/running, terminal success or closed, failure, and limits exceeded.
- MAS command dispatch for `status` - should replace the placeholder accepted response with a real non-blocking status query result for workflow-layer MAS Command Interception.
- External MAS CLI `status` command - should expose status inspection outside an Agent Workflow.
- Workflow Tree lookup - should support querying the current Agent Workflow Tree and querying a specific descendant workflow ID.
- Trajectory Artifact metadata - should remain the source of exact Run Directory and Trajectory Artifact path values returned by status.

**Acceptance criteria:**
- [ ] Child Status Events or equivalent lightweight status records include coarse lifecycle states such as `running`, `waiting_for_parent`, `closed`, `failed`, and `limits_exceeded`.
- [ ] Agent Workflows publish status updates when they start, fail, hit limits, or reach a terminal/closed state.
- [ ] Status data includes Workflow Tree ID, lifecycle state, Run Directory, and exact Trajectory Artifact path for each reported Agent Workflow.
- [ ] Status data includes `latest_submission` when a workflow has produced a submission.
- [ ] Status data includes `latest_error` when a workflow has failed or recorded an error.
- [ ] `mini-mas status` reports the current Agent Workflow Tree without blocking on child completion.
- [ ] `mini-mas status <workflow-id>` reports a specific descendant when it exists.
- [ ] Missing workflow behavior is explicit and test-covered; a missing workflow ID should not silently return an empty successful tree.
- [ ] Full message history and detailed trajectory history remain only in Trajectory Artifacts, not in DBOS events or status records.
- [ ] Tests cover tree status, specific workflow status, latest submission, latest error, limits exceeded, and missing workflow behavior.
- [ ] Existing MAS behavior for `run`, Detached Spawn, artifact paths, Standalone MAS Command rejection, and ordinary bash execution remains intact.

**Out of scope:**
- Implementing `mini-mas spawn --wait`.
- Implementing `mini-mas wait`.
- Implementing Continuation Signal or Close Signal behavior.
- Implementing the full Remote Interactive Agent lifecycle after first submission.
- Solving Shared Workspace isolation.
- Adding dedicated `mini-mas history`, `mini-mas logs`, `mini-mas grep`, or trajectory inspection commands.
- Storing full trajectory history in DBOS events or status records.
