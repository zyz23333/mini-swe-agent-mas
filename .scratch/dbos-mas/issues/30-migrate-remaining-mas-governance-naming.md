# Migrate remaining MAS governance naming

Status: ready-for-agent
Category: enhancement
Type: AFK

## Parent

.scratch/dbos-mas/PRD.md

## What to build

Complete the remaining behavior-preserving naming migration after the MAS glossary and ADRs moved from workflow/coordination language to **MAS Governance**, **Agent Interaction**, **Agent**, **Agent ID**, **Authority Model**, and **Delegated Non-Transitive Authority**.

This slice should update stale terminology in code comments, docstrings, CLI/help text, model-visible messages, result payload keys, tests, and local planning documents so readers see one coherent vocabulary. This project has no external users yet, so the slice may make breaking naming changes to user-visible MAS fields, command output keys, internal function names, test names, and error codes when doing so makes the MAS vocabulary coherent.

Keep DBOS implementation terms only at the DBOS boundary, where they name real DBOS APIs or metadata such as `DBOS.workflow_id` and `parent_workflow_id`. MAS-facing code and output should prefer **Agent ID** language, even if the underlying Agent ID is still stored in DBOS as a workflow ID.

The migration should be behavior-preserving but not API-name-preserving: improve naming consistency without changing MAS behavior, authority semantics, artifact path structure, command parsing rules, or DBOS workflow metadata usage. Any intentionally changed output shape or error code must be covered by updated tests.

Known areas to review:

- MAS source docstrings and help text in `src/minisweagent/mas/artifacts.py`, `status_events.py`, `cli.py`, `mas_agent.py`, `runtime.py`, `signals.py`, `commands.py`, and `agent_interactions.py`.
- User-visible output strings, result payload keys, exception info strings, command argument help, and tests that still say `Agent Workflow`, `Child Agent Workflow`, `Root Agent Workflow`, `Workflow Tree ID`, `workflow_id`, or `coordination` where the new domain term should be used.
- MAS-facing names such as `validate_workflow_id`, `make_root_workflow_id`, `child_workflow_ids`, `still_running_child_workflow_ids`, `continued_workflow_id`, `closed_workflow_id`, and related output keys. Rename these to **Agent ID** terminology unless the name is directly bound to a DBOS API.
- `.scratch/dbos-mas/PRD.md` and `.scratch/dbos-mas/mas-deep-module-refactor-map.md`, which still describe the MAS design with pre-governance terminology.
- Existing completed issue files under `.scratch/dbos-mas/issues/` only when they are used as current planning/reference material; avoid rewriting historical execution comments unless they actively mislead future agents.
- External unsupported-runtime names such as `external_coordination_unsupported`; these may be renamed because compatibility is not required, but the replacement should use the new vocabulary, for example external **Agent Interaction** wording, and tests must assert the new result shape.

## Agent Brief

**Category:** enhancement
**Summary:** Migrate remaining MAS-facing naming to the MAS Governance glossary while preserving behavior.

**Current behavior:**
The MAS implementation and planning docs have already adopted the new domain glossary in `CONTEXT.md` and the current ADRs, but source comments, docstrings, CLI/help text, model-visible messages, result payload keys, tests, and local planning documents still contain older workflow/coordination wording. Examples include `Agent Workflow`, `Child Agent Workflow`, `Root Agent Workflow`, `Workflow Tree ID`, `workflow_id`, `coordination`, `external_coordination_unsupported`, and MAS-facing payload keys such as `child_workflow_ids`, `still_running_child_workflow_ids`, `continued_workflow_id`, and `closed_workflow_id`.

The underlying implementation still uses DBOS workflows and DBOS workflow metadata. Those DBOS terms are valid at the DBOS boundary, especially where the code refers to real DBOS APIs, DBOS decorators, `DBOS.workflow_id`, or DBOS `parent_workflow_id` metadata.

**Desired behavior:**
MAS-facing language should consistently use the current glossary: **MAS Governance**, **Agent Interaction**, **Agent**, **Agent ID**, **Agent Tree**, **Authority Model**, and **Delegated Non-Transitive Authority**. User-visible output, model-visible observations, CLI help, result payload keys, test names, and local planning docs should prefer **Agent ID** terminology over `workflow_id` terminology unless the text is explicitly describing a DBOS implementation boundary.

This migration is behavior-preserving but not API-name-preserving. Because MAS has no external compatibility contract yet, the implementation may make breaking naming changes to MAS-facing output keys, internal function names, test names, and error codes when that makes the vocabulary coherent. Any intentionally changed output shape or error code must be covered by updated tests.

**Key interfaces:**
- MAS command result dictionaries — should keep the existing high-level `output`, `returncode`, `exception_info`, and `extra` contract, while renaming MAS-facing `extra` keys to Agent ID terminology where appropriate.
- MAS command output text — should use **Agent**, **Agent ID**, **Agent Tree**, **Agent Interaction**, and **MAS Governance** terms except at the DBOS boundary.
- MAS CLI and help text — should describe user-facing concepts as Agents and Agent IDs, not Agent Workflows or Workflow Tree IDs.
- MAS artifact helpers and status/event helpers — may keep DBOS-specific names only where they model actual DBOS workflow IDs, DBOS workflow metadata, DBOS decorators, or artifact path derivation from DBOS-backed identifiers.
- External unsupported command/runtime result — should use Agent Interaction wording rather than coordination wording, including a renamed error code and tests for the new result shape if the current code still exposes `external_coordination_unsupported`.
- Local MAS planning docs — should be synchronized with `CONTEXT.md` and the current ADR terminology where they remain active planning/reference material.
