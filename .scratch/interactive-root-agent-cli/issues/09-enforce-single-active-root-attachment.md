# Enforce single active Root attachment and resume gating

Status: ready-for-agent

## Parent

.scratch/interactive-root-agent-cli/PRD.md
.scratch/interactive-root-agent-cli/DESIGN.md

## What to build

Enforce the first-version attachment model for Interactive Root Agents. A Root Agent can have at most one active terminal attachment or one-shot command attachment. Resume is allowed only when the Root Agent is Waiting for Command. Running commands and waited spawns should make the Root unavailable for another attachment until they return or time out.

## Acceptance criteria

- [ ] A Root Agent accepts `resume` only in `waiting_for_command`.
- [ ] A Root Agent rejects or clearly reports unavailable attachment while it is `running`.
- [ ] A Root Agent rejects or clearly reports unavailable attachment while it is `waiting_for_child`.
- [ ] Concurrent attachment attempts cannot both submit commands to the same Root while it is accepting one command.
- [ ] If lifecycle-state gating is insufficient to prevent races, the implementation adds a small attachment lease or serialized accept handshake that is not Agent Metadata and not a Root index.
- [ ] Competing clients receive an unavailable result or time out with a clear message; they do not execute Root actions directly.
- [ ] One-shot `mini-mas spawn` occupies the Root attachment while its submitted command is running.
- [ ] One-shot `mini-mas spawn --wait` occupies the Root attachment until the waited spawn returns or times out.
- [ ] A detached Root Agent returns to `waiting_for_command` when ready for later resume.

## Agent Brief

**Category:** enhancement
**Summary:** Enforce single active attachment for each Interactive Root Agent and make resume availability race-safe.

**Current behavior:**
Interactive Root Agent resume already validates the target Agent ID, rejects non-root or non-Interactive targets, and checks the latest lifecycle state before allowing terminal entry. One-shot external spawn already creates an Interactive Root Agent and submits the first spawn command through the Root Command Signal and Root Command Result path. Waited spawn already publishes `waiting_for_child` during its waited phase and returns to `waiting_for_command` afterward.

The remaining gap is concurrency safety around attachment. Lifecycle-state checks reject obviously unavailable states such as `running` and `waiting_for_child`, but they do not by themselves prove that two external clients cannot both observe `waiting_for_command` and both submit Root Command Signals before the Root Agent has accepted one command and transitioned out of idle.

**Desired behavior:**
Each Interactive Root Agent should have at most one active attachment at a time in the first version. A terminal resume attachment and a one-shot command attachment are both attachments for this purpose.

`mini-mas resume <root-agent-id>` should be accepted only when the Interactive Root Agent is available for command input. If the Root Agent is already running a command, waiting on children, failed, closed, limits-exceeded, unknown, or otherwise not safely attachable, the CLI should return a clear unavailable result and should not enter the terminal.

Concurrent attachment attempts must not both submit executable commands to the same Root Agent while it is accepting one command. If lifecycle-state gating alone cannot provide that guarantee, add a small attachment lease or serialized accept handshake. That mechanism must be separate from Agent Metadata and must not introduce a Root index, global root, interaction-mode flag, or `is_root` flag.

Competing clients should receive an unavailable result or a bounded timeout with a clear message. They must not execute Root Agent actions directly in the external CLI process, and they must not bypass the Root Command Signal and Root Command Result path.

One-shot `mini-mas spawn ...` should occupy the Root attachment from the point where the external CLI claims/submits the Root command until the submitted command returns or the external result wait times out. One-shot `mini-mas spawn --wait ...` should occupy the Root attachment through the waited phase, including while the Root Agent is `waiting_for_child`. After a terminal detaches or a one-shot command finishes, the Interactive Root Agent should become available for later resume when it returns to `waiting_for_command`.

**Key interfaces:**
- Interactive Root Agent lifecycle state — remains the user-visible availability signal and should continue to distinguish `waiting_for_command`, `running`, and `waiting_for_child`.
- Resume preparation API — should reject unavailable Root Agents before the terminal accepts input and should participate in any race-safe attachment claim if one is needed.
- Root Command Signal submission API — should not allow an external client to submit a command unless that client has the active attachment or has passed the serialized accept handshake.
- Root Command Result event — remains the command-scoped result path for accepted commands and timeout reporting.
- One-shot external spawn path — should use the same attachment gating as resume, because one-shot spawn is an attachment while the submitted Root command is running or waiting.
- Attachment lease or serialized accept handshake, if added — should be short-lived, Root-scoped, recoverable after timeout or command completion, and should not be stored as Agent Metadata or as a Root index.

**Acceptance criteria:**
- [ ] `mini-mas resume <root-agent-id>` accepts an Interactive Root Agent only when it is safely available for command input.
- [ ] Resume rejects or clearly reports unavailable attachment while the Root Agent lifecycle state is `running`.
- [ ] Resume rejects or clearly reports unavailable attachment while the Root Agent lifecycle state is `waiting_for_child`.
- [ ] Resume rejects failed, closed, limits-exceeded, unknown, non-root, and non-Interactive targets without entering the terminal.
- [ ] Concurrent attachment attempts against the same Root Agent cannot both submit executable commands while the Root Agent is accepting one command.
- [ ] If lifecycle-state gating alone does not prove the concurrency guarantee, the implementation adds a small Root-scoped attachment lease or serialized accept handshake.
- [ ] Any attachment lease or handshake is not represented in Agent Metadata, does not require a Root index, and does not introduce root or interaction-mode flags.
- [ ] Competing clients receive an unavailable result or bounded timeout with a clear message that includes the Root Agent ID when known.
- [ ] Competing clients do not execute Root Agent actions directly in the external CLI process.
- [ ] Accepted commands continue to enter the Root Agent through Root Command Signals and return through command-id-scoped Root Command Results.
- [ ] One-shot `mini-mas spawn ...` occupies the Root attachment while its submitted command is running.
- [ ] One-shot `mini-mas spawn --wait ...` occupies the Root attachment until the waited spawn returns or times out.
- [ ] A detached terminal leaves the Root Agent available for later resume after the Root returns to `waiting_for_command`.
- [ ] A completed one-shot command leaves the Root Agent available for later resume after the Root returns to `waiting_for_command`.
- [ ] Tests cover unavailable lifecycle states, concurrent attachment competition, one-shot detached spawn occupancy, one-shot waited spawn occupancy, timeout/unavailable messaging, and post-detach/post-completion resumability.

**Out of scope:**
- Multiple simultaneous terminal attachments to one Interactive Root Agent.
- Root Agent close, delete, cleanup, garbage collection, or retention behavior.
- Naked external `wait`, `continue`, or `close` governance commands.
- Prefix-free terminal shorthand commands.
- Workspace Isolation or cross-Agent file coordination.
- Exactly-once spawn recovery or Operation Ledger design.
- A Root Agent index, global Root Agent, `is_root` flag, interaction-mode flag, run ID, or Root-scoped artifact model.
- A new Root Command Result payload schema unless the existing MAS Agent command result shape proves insufficient for the unavailable or timeout cases.
