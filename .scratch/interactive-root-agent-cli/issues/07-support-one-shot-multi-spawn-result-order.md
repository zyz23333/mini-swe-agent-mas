## Agent Brief

**Category:** enhancement
**Summary:** Preserve one-shot external multi-spawn child result order without adding durable sibling-order metadata.

**Current behavior:**
One-shot external spawn is implemented as a convenience path through a newly created Interactive Root Agent. The External MAS CLI can submit a standalone `mini-mas spawn ...` command through the Root Command Signal/Result flow and print the Root Agent ID plus spawned Child Agent metadata.

The broader design requires repeated task arguments to create multiple direct Child Agents under the same Interactive Root Agent. Existing implementation may already preserve list order naturally, but the behavior should be made explicit and protected by tests at the external one-shot spawn boundary.

**Desired behavior:**
When a user runs external `mini-mas spawn "task A" "task B"`, the command should create exactly one Interactive Root Agent and create one direct Child Agent per submitted task argument under that Root Agent.

The returned Child Agent entries should preserve the submitted task argument order in the current command result and rendered CLI output. The first child entry should correspond to `"task A"`, the second child entry should correspond to `"task B"`, and so on for additional repeated task arguments.

This ordering is display/result ordering only. It must not become durable identity, authority, artifact, or Agent Metadata. Child Agent IDs must remain opaque `mas-<random-hex>` Agent IDs, and Agent Metadata must not include sibling-order fields such as spawn index, sibling index, task position, or result order.

**Key interfaces:**
- External `mini-mas spawn ...` command — should accept repeated task arguments and route the full standalone spawn command through an Interactive Root Agent.
- Root Command Result shape — should carry child entries in the same order as the submitted task arguments.
- Spawn result rendering — should print one Root Agent ID and one Child Agent metadata entry per submitted task, preserving the result order.
- Agent Metadata — should remain limited to stable identity and artifact fields, without durable sibling-order fields.
- Agent ID generation and validation — should keep Agent IDs opaque and must not encode parent identity, sibling order, or tree position.

**Acceptance criteria:**
- [x] External `mini-mas spawn "task A" "task B"` creates one Interactive Root Agent.
- [x] Each submitted task argument creates one direct Child Agent under that Root Agent.
- [x] Output includes exactly one Root Agent ID and one metadata entry per Child Agent.
- [x] Child Agent entries in the Root Command Result and rendered CLI output are returned in the same order as the submitted task arguments.
- [x] The ordering behavior is covered by tests that would fail if the child entries were reversed or otherwise reordered.
- [x] Child Agent IDs remain opaque and do not encode sibling order, parent identity, or tree position.
- [x] Agent Metadata does not include durable sibling-order fields such as spawn index, sibling index, task position, or result order.

**Out of scope:**
- Changing waited-spawn semantics for `--wait`, `--all`, or `--timeout`.
- Introducing durable sibling-order metadata, spawn indexes, tree-position fields, or order-aware Agent IDs.
- Adding a Root Agent index, global Root Agent, run ID, root-scoped artifact layout, or interaction-mode flag.
- Changing Direct Child Authority Policy.
- Adding naked external `wait`, `continue`, or `close` commands.
