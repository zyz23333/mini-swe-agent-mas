# Handle pre-root status and resume locally in plain terminal

Status: ready-for-agent

## What to build

Update plain `mini-mas` terminal behavior so `mini-mas status` and `mini-mas resume <root-agent-id>` entered before any Root Agent exists reuse the same External MAS CLI behavior as the top-level commands instead of creating a new Interactive Root Agent.

Before Root creation, standalone `mini-mas status` should run Root discovery, print the same discovery output as top-level `mini-mas status`, avoid creating or attaching to a Root Agent, and keep the plain terminal unbound for later input.

Before Root creation, standalone `mini-mas resume <root-agent-id>` should attempt the same resume path as top-level `mini-mas resume <root-agent-id>` without creating a new Root Agent. On success, the plain terminal should become attached to that existing Root and behave exactly like a resume terminal. On failure, it should print the same failure output as top-level resume and keep the plain terminal unbound for the next input.

All behavior after the terminal is attached to a Root remains unchanged: `mini-mas status`, `mini-mas resume ...`, and other non-exit input are sent to the attached Root through the Root Command Signal path.

## Acceptance criteria

- [ ] Plain `mini-mas` still starts an unbound terminal without creating an Interactive Root Agent.
- [ ] Pre-root empty input, whitespace-only input, `exit`, `quit`, and EOF keep their existing no-Root behavior.
- [ ] Pre-root standalone `mini-mas status` runs the same Root discovery behavior as top-level `mini-mas status`.
- [ ] Pre-root standalone `mini-mas status` does not call Interactive Root Agent startup, does not claim a Root attachment, and does not send a Root Command Signal.
- [ ] After pre-root `mini-mas status` prints discovery output, the plain terminal remains unbound and accepts another input.
- [ ] Pre-root standalone `mini-mas resume <root-agent-id>` runs the same resume validation and attachment behavior as top-level `mini-mas resume <root-agent-id>`.
- [ ] Successful pre-root `mini-mas resume <root-agent-id>` does not create a new Root Agent, prints the Root metadata banner, claims the existing Root attachment, and enters the attached terminal loop for that Root.
- [ ] Failed pre-root `mini-mas resume <root-agent-id>` prints the same failure output as top-level resume, does not create a new Root Agent, does not leave an attachment lease behind, and leaves the plain terminal unbound for later input.
- [ ] The first pre-root input that is not empty, local exit, standalone `mini-mas status`, or standalone `mini-mas resume <root-agent-id>` still creates a new parentless Interactive Root Agent and sends that input unchanged through the Root Command Signal path.
- [ ] After a Root is attached, `mini-mas status` and `mini-mas resume ...` entered in the terminal are sent through the attached Root Command Signal path rather than handled locally by the CLI process.
- [ ] Tests cover pre-root `status`, successful pre-root `resume`, failed pre-root `resume`, continued unbound input after local commands, and unchanged attached-terminal routing after Root attachment.

## Agent Brief

**Category:** fix
**Summary:** Treat pre-root plain-terminal `mini-mas status` and `mini-mas resume <root-agent-id>` as local External MAS CLI commands instead of first commands that create a new Root.

**Current behavior:**
Issue 12 changed plain `mini-mas` so it starts unbound and lazily creates a new Interactive Root Agent on the first effective command. Its acceptance criteria deliberately made first-command `mini-mas status` create a new Root and execute inside that Root as a Standalone MAS Command.

That behavior is wrong for the unbound terminal state. A user who has entered the plain terminal but has not yet selected or created a Root should be able to run the same Root discovery and resume entrypoints that exist at the top-level External MAS CLI surface. Running `mini-mas status` in that state should not manufacture a new empty Root Agent just to observe existing Roots.

**Desired behavior:**
Plain `mini-mas` has a pre-root local terminal state. In that state:

- Empty and whitespace-only input is ignored.
- `exit`, `quit`, and EOF exit locally without creating a Root.
- Standalone `mini-mas status` runs external Root discovery, prints the same output as top-level `mini-mas status`, and stays unbound.
- Standalone `mini-mas resume <root-agent-id>` runs external resume against the existing Root. If it succeeds, the terminal attaches to that Root. If it fails, the same failure output is printed and the terminal stays unbound.
- Any other effective input creates a new Root and sends the input unchanged through the Root Command Signal path.

After the terminal is attached to any Root, whether by lazy creation or pre-root resume, local status/resume handling no longer applies. Terminal input follows the existing attached behavior and is sent to the Root unless it is local `exit`, `quit`, or EOF.

**Key interfaces:**
- Plain External MAS CLI invocation - should keep the pre-root local input loop but classify local `status` and `resume` commands before deciding to create a Root.
- External Root discovery runtime - should be reused for pre-root `mini-mas status`.
- Resume preparation and attached terminal loop - should be reused for successful pre-root `mini-mas resume <root-agent-id>`.
- Root Command Signal sending API - should still receive all non-local commands unchanged, including attached-terminal `mini-mas status` and `mini-mas resume ...`.

**Acceptance criteria:**
- [ ] Plain `mini-mas` still starts an unbound terminal without creating an Interactive Root Agent.
- [ ] Pre-root empty input, whitespace-only input, `exit`, `quit`, and EOF keep their existing no-Root behavior.
- [ ] Pre-root standalone `mini-mas status` runs the same Root discovery behavior as top-level `mini-mas status`.
- [ ] Pre-root standalone `mini-mas status` does not call Interactive Root Agent startup, does not claim a Root attachment, and does not send a Root Command Signal.
- [ ] After pre-root `mini-mas status` prints discovery output, the plain terminal remains unbound and accepts another input.
- [ ] Pre-root standalone `mini-mas resume <root-agent-id>` runs the same resume validation and attachment behavior as top-level `mini-mas resume <root-agent-id>`.
- [ ] Successful pre-root `mini-mas resume <root-agent-id>` does not create a new Root Agent, prints the Root metadata banner, claims the existing Root attachment, and enters the attached terminal loop for that Root.
- [ ] Failed pre-root `mini-mas resume <root-agent-id>` prints the same failure output as top-level resume, does not create a new Root Agent, does not leave an attachment lease behind, and leaves the plain terminal unbound for later input.
- [ ] The first pre-root input that is not empty, local exit, standalone `mini-mas status`, or standalone `mini-mas resume <root-agent-id>` still creates a new parentless Interactive Root Agent and sends that input unchanged through the Root Command Signal path.
- [ ] After a Root is attached, `mini-mas status` and `mini-mas resume ...` entered in the terminal are sent through the attached Root Command Signal path rather than handled locally by the CLI process.

**Out of scope:**
- Prefix-free shorthand such as `status` or `resume` inside the terminal.
- Local handling of pre-root `mini-mas spawn ...`; that remains a work command that creates a new Root.
- Local handling of pre-root `mini-mas wait`, `mini-mas continue`, or `mini-mas close`.
- Changing external Root discovery output.
- Changing top-level resume validation, attachment, heartbeat, or release semantics.
- Changing attached-terminal command routing after a Root exists.
