## Agent Brief

**Category:** enhancement
**Summary:** Replace tree-encoded MAS Agent IDs and root/run-scoped artifacts with opaque Agent IDs and Agent-scoped artifact metadata.

**Current behavior:**
MAS Agent identity and artifact metadata still carry root/run and tree-position assumptions. Root Agent IDs use the `mas-<random-hex>` shape, but Child Agent IDs are derived from their Parent Agent ID with sibling suffixes such as `-cNNN`. Artifact metadata exposes root/run-oriented fields such as root workflow identity and run directory, and Trajectory Artifacts are grouped under a Root Agent/run directory. Some helper behavior derives root identity or parent identity from Agent ID shape.

**Desired behavior:**
Every MAS Agent, including Root Agents and Child Agents, should use the same opaque Agent ID shape: `mas-<random-hex>`. Agent IDs must not encode root identity, parent identity, sibling order, or Agent Tree position. DBOS workflow ID should equal the Agent ID for MAS Agents.

Agent Metadata should describe one Agent's stable identity and artifact locations: Agent ID, optional Parent Agent ID, Agent Artifact Directory, and Trajectory Artifact path. Trajectory Artifacts should live under Agent Artifact Directories keyed by Agent ID rather than under Root Agent, run, or tree-position directories.

Parent-child relationships and Direct Child Authority must continue to come from DBOS workflow parent metadata. The implementation should not use Agent ID prefixes, artifact paths, root/run fields, sibling indexes, `is_root`, interaction-mode flags, a Root Agent index, or a global root to establish authority or discover structure.

Multi-spawn command result order may preserve the order of submitted task arguments for immediate output, but sibling order must not be persisted as durable Agent metadata or encoded into Agent IDs.

**Key interfaces:**
- Agent ID validation and generation — should accept and produce opaque `mas-<random-hex>` IDs for both Root Agents and Child Agents.
- Child Agent spawning — should allocate each Child Agent an opaque Agent ID while preserving DBOS parent workflow metadata for Parent Agent to Child Agent relationships.
- Agent Metadata shape — should expose `agent_id`, optional `parent_agent_id`, `agent_artifact_directory`, and `trajectory_artifact_path` or equivalent stable public names aligned with the domain language.
- Trajectory Artifact persistence — should write each Agent's trajectory inside that Agent's own Agent Artifact Directory.
- Child status and command-result payloads — should report Agent Metadata without relying on root/run directory fields or tree-encoded workflow IDs.
- Direct Child Authority checks — should keep using DBOS workflow parent metadata to prove direct-child scope.

**Acceptance criteria:**
- [x] Root Agents and Child Agents both use opaque `mas-<random-hex>` Agent IDs.
- [x] Child Agent IDs do not include Parent Agent IDs, root IDs, sibling indexes, `-cNNN` suffixes, or other Agent Tree position markers.
- [x] DBOS workflow ID equals Agent ID for each MAS Agent.
- [x] Agent Metadata includes Agent ID, optional Parent Agent ID, Agent Artifact Directory, and Trajectory Artifact path.
- [x] Agent Metadata does not use root/run directory fields as the canonical artifact model.
- [x] Trajectory Artifacts live under per-Agent Artifact Directories keyed by Agent ID.
- [x] Direct Child Authority behavior continues to resolve parent-child relationships from DBOS workflow parent metadata rather than Agent ID prefixes or artifact paths.
- [x] `mini-mas status`, `mini-mas wait`, `mini-mas continue`, and `mini-mas close` continue to enforce direct-child-only authority.
- [x] Multi-spawn command results may preserve submitted task order in the returned list.
- [x] Sibling order is not stored as durable Agent metadata and is not encoded into Agent IDs.
- [x] Tests cover opaque Agent ID generation/validation, per-Agent artifact metadata, artifact path layout, multi-spawn output ordering, and direct-child authority regression behavior.

**Out of scope:**
- Implementing the full Interactive Root Agent terminal, Resume, Root Command Signal, or Root Command Result workflow.
- Adding external naked `wait`, `continue`, or `close` commands outside an Interactive Root Agent authority context.
- Adding a Root Agent index, global root Agent, root/run grouping model, `is_root` flag, or interaction-mode flag.
- Designing exactly-once spawn recovery or Operation Ledger behavior.
- Implementing Workspace Isolation.
