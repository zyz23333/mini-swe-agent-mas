## What to build

Implement the narrow command transport between the External MAS CLI and an Interactive Root Agent. The CLI should send one bash-shaped command as a Root Command Signal, the Root Agent should execute it through the existing MAS Agent action flow, and the Root Agent should publish a command-id-scoped Root Command Result event that the CLI waits on.

- [x] The Interactive Root Agent executes the command itself; the CLI does not execute Root Agent actions directly.
- [x] Ordinary bash commands execute through the existing bash-shaped action flow.
- [x] Standalone `mini-mas ...` commands still enter MAS Command Interception.

- [x] The Root Command Result uses the existing MAS Agent command result shape.
- [x] Recoverable command execution errors publish a Root Command Result with non-zero return code and persist the error observation when possible.
- [x] The Root command loop remains alive after a recoverable command error and returns to `waiting_for_command`.

## Agent Brief

**Category:** enhancement
**Summary:** Deliver Root Command Signals and command-id-scoped Root Command Results end to end.

**Current behavior:**
The minimal Interactive Root Agent startup path exists: plain `mini-mas` can create a parentless Interactive Root Agent, publish `waiting_for_command`, write Agent-scoped artifacts, and print a Root Agent metadata banner. The command transport is not complete yet. The External MAS CLI does not yet submit terminal commands to the Interactive Root Agent through a Root Command Signal, and the Interactive Root Agent does not yet run a durable command loop that executes each received command and publishes a matching Root Command Result.

Existing workflow-layer MAS Command Interception already distinguishes standalone `mini-mas ...` commands from ordinary bash commands and invalid composed commands. Existing MAS Agent command results already use the result shape with output, return code, exception information, and extra metadata.

**Desired behavior:**
The External MAS CLI should be able to send exactly one bash-shaped command to a waiting Interactive Root Agent as a Root Command Signal. The signal should include a unique command ID and the target Root Agent ID. The Interactive Root Agent should validate that the signal's `root_agent_id` matches its own workflow ID before executing the command.

The Interactive Root Agent, not the CLI process, should execute the command through the existing MAS Agent bash-shaped action flow. Ordinary bash commands should execute as ordinary bash actions. Standalone `mini-mas ...` commands should still enter MAS Command Interception. Commands that contain `mini-mas` inside shell composition, such as `mini-mas status && echo done`, should remain invalid for MAS Command Interception.

While executing ordinary bash commands or detached MAS commands, the Root Agent should publish `running` lifecycle state. After execution, it should publish a Root Command Result event scoped by the submitted command ID. Waiting CLI callers must only be satisfied by the event for the command ID they submitted, not by another pending or completed command's result.

The Root Command Result should reuse the existing MAS Agent command result shape where possible. Recoverable command execution errors should publish a Root Command Result with a non-zero return code and should persist the error observation when possible. After a recoverable error, the Root command loop should stay alive and return to `waiting_for_command`.

**Key interfaces:**
- Root Command Signal shape — carries one bash-shaped command, a command ID, the target `root_agent_id`, and enough source context to identify the External MAS CLI path.
- Interactive Root Agent workflow — should become a command-receiving loop rather than only a minimal idle publisher.
- Root Command Result event — should be scoped by command ID and include the Root Agent ID, original command, command ID, and existing MAS Agent command result payload.
- Existing MAS Agent command result shape — should remain the payload contract for successful MAS commands, ordinary bash execution, invalid commands, and recoverable execution errors.
- MAS Command Interception — standalone `mini-mas ...` commands should continue to be routed through the workflow-layer command dispatcher, while composed commands containing `mini-mas` remain invalid.
- Root Agent lifecycle status — should transition to `running` while ordinary bash commands or detached MAS commands execute, then back to `waiting_for_command` after recoverable completion.
- Trajectory Artifact persistence — should record ordinary bash actions and error observations in the Root Agent's existing Agent-scoped Trajectory Artifact when possible.

**Acceptance criteria:**
- [ ] The CLI can send a Root Command Signal containing one command, one command ID, and a target Root Agent ID to a waiting Interactive Root Agent.
- [ ] Root Command Signals validate that `root_agent_id` matches the target Interactive Root Agent workflow ID before command execution.
- [ ] The Interactive Root Agent executes the command itself; the CLI does not execute Root Agent actions directly.
- [ ] Ordinary bash commands execute through the existing bash-shaped action flow.
- [ ] Standalone `mini-mas ...` commands still enter MAS Command Interception.
- [ ] Composed commands containing `mini-mas`, such as `mini-mas status && echo done`, remain invalid for MAS Command Interception.
- [ ] The Root Agent publishes `running` lifecycle state while ordinary bash commands execute.
- [ ] The Root Agent publishes `running` lifecycle state while detached MAS commands execute.
- [ ] The Root Agent publishes a Root Command Result event after command execution.
- [ ] Root Command Result events are scoped by command ID so one pending command cannot be satisfied by another command's result.
- [ ] Root Command Results use the existing MAS Agent command result shape where possible.
- [ ] Recoverable command execution errors publish a Root Command Result with a non-zero return code.
- [ ] Recoverable command execution errors persist the error observation in the Root Agent Trajectory Artifact when possible.
- [ ] The Root command loop remains alive after a recoverable command error.
- [ ] After recoverable command completion or error, the Root Agent returns to `waiting_for_command`.
- [ ] Tests cover signal delivery, root ID validation, command ID result scoping, ordinary bash execution, standalone MAS command interception, invalid composed `mini-mas` commands, lifecycle transitions, command result shape, and recoverable error behavior.

**Out of scope:**
- Implementing external `mini-mas status` root discovery.
- Implementing `mini-mas resume <root-agent-id>` as a user-facing terminal entrypoint.
- Implementing one-shot external `mini-mas spawn ...` output formatting beyond what is necessary to prove command transport.
- Implementing concurrent terminal attachment checks.
- Implementing Root Agent close, delete, cleanup, garbage collection, or retention policy.
- Adding prefix-free prompt commands such as `status`.
- Introducing a new Root Command Result payload schema.
- Adding exactly-once recovery semantics for bash side effects or spawn side effects.
