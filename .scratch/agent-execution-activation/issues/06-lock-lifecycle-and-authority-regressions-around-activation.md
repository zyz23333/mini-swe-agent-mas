# Lock lifecycle and authority regressions around activation

Status: ready-for-agent
Category: enhancement

## What to build

Add focused regression coverage that keeps AI Agent Execution as runtime state rather than Agent lifecycle or MAS Governance authority. The implementation should remain aligned with ADR 0009, preserve Direct Child Authority Policy and the External MAS CLI entry model, and avoid implying exactly-once side-effect recovery or Workspace Isolation.

## Acceptance criteria

- [ ] Tests prove no `queued` Agent lifecycle state is introduced.
- [ ] Tests prove Agent status output remains based on Agent-published lifecycle states and existing metadata.
- [ ] Tests prove AI Agent Execution activation state is not stored in Agent metadata, Child Status Event data, or External MAS CLI status output.
- [ ] Tests prove activation does not grant broader Authority over Descendant Agents or peers.
- [ ] Tests prove the existing External MAS CLI entry model still submits governance commands through Interactive Root Agents.
- [ ] Documentation or test names use the project glossary terms from `CONTEXT.md` and remain consistent with ADR 0009.
- [ ] The implementation does not claim to solve exactly-once side-effect recovery for model calls, bash actions, or spawn.
- [ ] The implementation does not claim to solve Workspace Isolation.

> ## Agent Brief
>
> **Category:** enhancement
> **Summary:** Add regression coverage that keeps AI Agent Execution activation out of Agent lifecycle, Agent metadata, status surfaces, and MAS Governance authority.
>
> **Current behavior:**
> The AI Agent Execution activation work has already split Interactive Agent work and autonomous AI Agent work onto separate queues, added the foreground `mini-mas agent activate` command, proved staged AI Agent work executes only while activation is running, and kept `mini-mas status` focused on Interactive Root Agent discovery.
>
> The remaining risk is regression drift. Future changes could accidentally describe queued AI Agent work as an Agent lifecycle state, store activation liveness in Agent metadata or Child Status Event data, expose activation state through External MAS CLI status output, or treat activation as broader MAS Governance authority. Those regressions would violate ADR 0009, the Direct Child Authority Policy, and the External MAS CLI entry model.
>
> **Desired behavior:**
> Focused tests should pin the boundary that AI Agent Execution activation is runtime state only. Activation should authorize consumption of autonomous AI Agent work while the foreground command is running, but it must not become an Agent lifecycle state, Agent metadata field, Child Status Event field, External MAS CLI status field, or Authority Grant.
>
> Agent status output should continue to be based on Agent-published lifecycle states and existing Agent metadata. External MAS CLI governance commands should continue to enter through Interactive Root Agents, preserving the parent authority context rather than introducing naked external authority over Child Agents, Descendant Agents, or peers.
>
> Test names, documentation, and assertions should use the project glossary terms from `CONTEXT.md` and remain consistent with ADR 0009. The work should avoid implying that activation solves exactly-once side-effect recovery for model calls, bash actions, or spawn, and should avoid implying that activation solves Workspace Isolation.
>
> **Key interfaces:**
> - Agent lifecycle state publishing - should not gain a `queued` lifecycle state or activation-liveness state.
> - Agent metadata and artifact metadata - should remain identity and artifact description data, not queue placement or activation-liveness storage.
> - Child Status Event data - should remain lightweight Agent status data and should not report AI Agent Execution activation state.
> - External MAS CLI `status` output - should remain focused on Interactive Root Agent discovery and existing metadata.
> - External MAS CLI governance entry model - should continue submitting commands through Interactive Root Agents instead of adding naked external authority paths.
> - Direct Child Authority Policy - activation should not grant authority over Descendant Agents or peer Agents.
> - ADR 0009 terminology - tests and documentation should describe activation as AI Agent Execution runtime state, not lifecycle, metadata, status, or authority.
>

> - [ ] Tests prove no `queued` Agent lifecycle state is introduced.

> - [ ] Tests prove AI Agent Execution activation state is not stored in Agent metadata.

> - [ ] Tests prove AI Agent Execution activation state is not exposed through External MAS CLI status output.

> - [ ] Tests prove activation does not grant broader Authority over peer Agents.
