## Agent Brief

**Category:** enhancement
**Summary:** Add `mini-mas agent activate` as the explicit foreground activation command for AI Agent Execution.

**Current behavior:**
Ordinary External MAS CLI runtime activation is constrained to Interactive Agent work on `mini_mas_interactive_workflows`. Spawned autonomous Child Agent work is queued on `mini_mas_ai_agent_workflows`, but there is no explicit foreground External MAS CLI command that activates AI Agent Execution for that queue. As a result, users can stage AI Agent work but do not yet have the intended `mini-mas agent activate` command for authorizing queued autonomous Agents to advance.

**Desired behavior:**
The External MAS CLI should expose `mini-mas agent activate`.

Running `mini-mas agent activate` should launch the MAS runtime for the active MAS Runtime State Store with an explicit queue-listening policy for `mini_mas_ai_agent_workflows` only. It should remain running in the foreground even when no AI Agent work is currently queued, so users can start activation before work appears. Stopping the foreground process with Ctrl-C should deactivate execution capacity without closing, deleting, cancelling, accepting, continuing, or otherwise making governance decisions about Agents.

The command should start without a second confirmation prompt. Invoking the command is the explicit authorization. On startup it should print a clear notice that queued AI Agent work may call models, execute bash actions, and modify the Shared Workspace. When available, the notice should include the active workspace, MAS Runtime State Store, AI Agent queue, side-effect warning, and Ctrl-C deactivation guidance.

**Key interfaces:**
- External MAS CLI command structure - should support `mini-mas agent activate` without changing the semantics of plain `mini-mas`, `mini-mas status`, `mini-mas spawn`, or `mini-mas resume`.
- MAS queue catalog - `mini_mas_ai_agent_workflows` should come from the centralized queue name definition rather than duplicated string literals.
- Runtime launch boundary - activation should apply an explicit DBOS queue-listening policy before launch, using the same policy-before-launch principle as ordinary interactive runtime activation.
- Foreground activation loop or wait boundary - the activation command should keep the process alive when there is no queued AI Agent work, and should exit cleanly on normal interruption.
- Startup notice formatter - activation output should be testable independently from private DBOS internals where practical.
- Agent lifecycle and governance operations - activation must not create, continue, close, accept, cancel, or delete Agents by itself.

**Acceptance criteria:**
- [ ] The External MAS CLI exposes `mini-mas agent activate`.
- [ ] `mini-mas agent activate` launches DBOS with an explicit queue-listening policy for `mini_mas_ai_agent_workflows` only.
- [ ] The AI Agent queue-listening policy is applied before DBOS launch.
- [ ] The command does not listen to `mini_mas_interactive_workflows`.
- [ ] The command remains running in the foreground when no AI Agent work is currently queued.
- [ ] The command starts without a second confirmation prompt.
- [ ] The command prints a startup notice warning that queued AI Agent work may call models, execute bash actions, and modify the Shared Workspace.
- [ ] The startup notice includes the active workspace, MAS Runtime State Store, AI Agent queue, side-effect warning, and Ctrl-C deactivation guidance when those values are available.
- [ ] Tests prove activation does not create any Agent by itself.
- [ ] Tests prove activation does not continue, close, accept, cancel, or delete any Agent by itself.
- [ ] Existing tests continue to prove ordinary `mini-mas` listens only to `mini_mas_interactive_workflows`.
- [ ] Existing `mini-mas status`, `mini-mas spawn`, and `mini-mas resume` behavior is preserved.

**Out of scope:**
- Implementing a background daemon or system service for AI Agent Execution.
- Adding `mini-mas agent deactivate`; foreground Ctrl-C is sufficient for this issue.
- Adding a second confirmation prompt.
- Reporting AI Agent Execution activation in `mini-mas status`.
- Reporting queued AI Agent work in `mini-mas status`.
- Adding a persistent prompt indicator for AI Agent Execution.
- Adding a new Agent lifecycle state for queued work or activation liveness.
- Changing Direct Child Authority Policy.
- Changing spawn queue semantics except where needed to verify activation consumes only the AI Agent queue.
- Solving DBOS exactly-once side-effect recovery, model-call replay safety, bash replay safety, spawn recovery semantics, or Workspace Isolation.
