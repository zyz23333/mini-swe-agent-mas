# Constrain ordinary `mini-mas` to the Interactive Agent queue

Status: ready-for-agent

## What to build

Make ordinary `mini-mas` runtime activation consume only Interactive Agent work. The default External MAS CLI path should launch DBOS with an explicit queue-listening policy for `mini_mas_interactive_workflows`, start Interactive Root Agents through that queue instead of direct workflow startup, and avoid consuming autonomous AI Agent work.

## Acceptance criteria

- [ ] MAS queue names are centralized so `mini_mas_interactive_workflows` and `mini_mas_ai_agent_workflows` are not duplicated ad hoc across runtime code.
- [ ] Ordinary `mini-mas` runtime activation declares a queue-listening policy before DBOS launch and listens only to `mini_mas_interactive_workflows`.
- [ ] Interactive Root Agent startup uses queued startup through `mini_mas_interactive_workflows` rather than direct DBOS workflow startup.
- [ ] Existing Interactive Root Agent availability still works for plain `mini-mas`, `mini-mas resume <root-agent-id>`, and one-shot command entry paths.
- [ ] Tests prove ordinary `mini-mas` does not listen to or consume `mini_mas_ai_agent_workflows`.
- [ ] Tests avoid depending on private DBOS implementation details such as internal thread names.

None - can start immediately

## Agent Brief

**Category:** enhancement
**Summary:** Constrain ordinary `mini-mas` runtime activation to Interactive Agent work only.

**Current behavior:**
Ordinary External MAS CLI runtime paths initialize and launch DBOS for Interactive Root Agent startup, resume-related command handling, one-shot command entry, and discovery-style commands. Interactive Root Agent startup currently uses direct DBOS workflow startup, and MAS queue names are not centralized around the intended interactive/autonomous runtime boundary. This risks ordinary `mini-mas` runtime activation consuming autonomous AI Agent work when DBOS queue listening or recovery behavior is not explicitly constrained.

**Desired behavior:**
Ordinary `mini-mas` runtime activation should declare an explicit queue-listening policy before DBOS launch and should listen only for Interactive Agent work on `mini_mas_interactive_workflows`.

Interactive Root Agent startup should be queued through `mini_mas_interactive_workflows` instead of direct DBOS workflow startup. Plain `mini-mas`, `mini-mas resume <root-agent-id>`, and one-shot command paths should continue to make Interactive Root Agents available without enabling autonomous AI Agent Execution.

Autonomous AI Agent work must remain on `mini_mas_ai_agent_workflows` and must not be consumed by ordinary `mini-mas` runtime activation.

**Key interfaces:**
- MAS queue catalog - central source of truth for `mini_mas_interactive_workflows` and `mini_mas_ai_agent_workflows`, avoiding ad hoc duplicated strings in runtime code.
- Runtime activation policy - a stable interface that maps ordinary `mini-mas` runtime activation to the interactive queue only.
- DBOS launch wrapper or equivalent runtime boundary - applies the queue-listening policy before DBOS launch.
- Interactive Root Agent startup API - starts `interactive_root_agent_workflow` through queued startup on the interactive queue.
- External MAS CLI entry paths - plain `mini-mas`, `mini-mas resume <root-agent-id>`, and one-shot command flows must preserve existing Interactive Root Agent availability behavior.

**Acceptance criteria:**
- [ ] MAS queue names are centralized so `mini_mas_interactive_workflows` and `mini_mas_ai_agent_workflows` are not duplicated ad hoc across runtime code.
- [ ] Ordinary `mini-mas` runtime activation declares a queue-listening policy before DBOS launch.
- [ ] Ordinary `mini-mas` runtime activation listens only to `mini_mas_interactive_workflows`.
- [ ] Ordinary `mini-mas` runtime activation does not listen to or consume `mini_mas_ai_agent_workflows`.
- [ ] Interactive Root Agent startup uses queued startup through `mini_mas_interactive_workflows` rather than direct DBOS workflow startup.
- [ ] Existing Interactive Root Agent availability still works for plain `mini-mas`.
- [ ] Existing Interactive Root Agent availability still works for `mini-mas resume <root-agent-id>`.
- [ ] Existing Interactive Root Agent availability still works for one-shot command entry paths such as external spawn.
- [ ] Tests prove ordinary `mini-mas` does not listen to or consume autonomous AI Agent work.
- [ ] Tests avoid depending on private DBOS implementation details such as internal thread names.

**Out of scope:**
- Implementing `mini-mas agent activate`.
- Changing how spawned Child Agents are queued as autonomous AI Agent work beyond what is required to keep ordinary `mini-mas` from consuming that queue.
- Reporting AI Agent Execution activation or queued AI Agent work in `mini-mas status`.
- Adding an Agent lifecycle state for queued work.
- Changing Direct Child Authority Policy.
- Solving DBOS side-effect recovery semantics, exactly-once model calls, exactly-once bash actions, or Workspace Isolation.
